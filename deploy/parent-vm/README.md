# Proposed single-host CaseLink pilot

This package runs the actual parent CaseLink Next app and existing isolated services on one Ubuntu 24.04 LTS VM. It creates no infrastructure, credentials, database permissions, processing approval or provider authorization. Every example is disabled and expired. The existing Vercel school site and `https://www.thecaselink.com` account recovery remain in place. This is a bounded pilot package, not evidence of family readiness or capacity for thousands.

Keep one host and one worker, test the actual document workload, and increase capacity only when measurements justify it. A 4 GiB host is a candidate to verify, not a proved minimum. The host is proposed for continuous background work and private-service isolation, not because 50 users require additional servers.

## Process boundaries

| Service account / profile | Ingress and authority |
| --- | --- |
| `caselink-web` | Next on `127.0.0.1:3100`; public Supabase key and public settings only. No model, database login, storage or carrier credential. |
| `caselink-frontdoor` | `127.0.0.1:3200`; exact public host, fixed app/review origins, no private credentials. Caddy is the only public ingress. |
| `caselink-review` | `127.0.0.1:3400`; dedicated finalizer login, public key, independently enabled protected collection. Same-site protected routes and existing user/session checks. |
| `caselink-worker` | Exactly one durable worker, dedicated worker login, model key and broker secret. Optional sender secret only after separate sending authority. No S3, finalizer or carrier credential. |
| `caselink-broker` | `127.0.0.1:3310`; dedicated storage-broker login, dedicated Supabase S3 credentials, broker secret. Existing immutable-artifact guard remains required. |
| `caselink-sender` | `127.0.0.1:3500`; dedicated sender login, sender secret and narrowly configured Sinch credentials/destinations. Independently disabled by default. |
| `caselink-retention` | Independent timer/oneshot; dedicated retention login. Protected encrypted PDFs and corresponding keys only; no storage/Auth/model/carrier credential. |
| `caselink-ordinary-retention` | Separate timer/oneshot; dedicated retention login and S3 credentials. Leased ordinary document/artifact deletion and parent-purpose cleanup only; no Auth/model/carrier credential. |
| `caselink-parser` | Rootless Docker daemon, no application/provider credentials. A digest-pinned parser runs with the existing no-network, read-only, unprivileged, memory/PID/CPU/time limits. |

Each application role owns `/etc/caselink/ROLE/` mode 0700 and `profile.json` mode 0600. The parent directory is root-owned; do not share a secret bundle or use `.env` files. The launcher rejects symlinks, other owners, extra config fields, expired/disabled profiles, database URL options and wrong projects. Dedicated database logins must retain the existing NOINHERIT/nonprivileged/exact role-membership checks in the underlying services; the launcher does not grant roles or bypass those checks.

The web build and runtime use the same public-only profile. The build marker binds `.next/BUILD_ID` to its public configuration. A changed site/key requires a rebuild. An independently renewed operating deadline does not. The original recovery origin is fixed. No local connected approval flags are synthesized.

3. Install a rootless Docker daemon for `caselink-parser` with cgroupv2/systemd resource delegation. Give only `caselink-worker` access to its Unix socket using a narrow group/ACL; make the parser user's runtime directory traversable only to that group. Keep the daemon's home free of all application secrets. Do not expose its TCP API or grant access to the system/root Docker socket. 4. Place release code under root ownership and make it read-only to service accounts. Run `/usr/bin/node --import tsx scripts/parent-hosted-services.ts /ABSOLUTE/PRIVATE/web/profile.json build`. 5. Point `/opt/caselink/current` to that complete release. Install the included systemd units, slice and worker-only `caselink-parent@worker.service.d/rootless-docker.conf` drop-in. The worker uses `ProtectHome=read-only` so its rootless Unix socket under `/run/user` remains reachable; every other role retains `ProtectHome=yes`. Service secret/home directories must still be mode 0700 with distinct owners. Do not start them yet. Use `systemd-analyze verify` on Ubuntu 24.04; verify each unit can read only its own config and writable state. `ProtectProc=invisible`, distinct users, disabled core dumps, read-only code and private temporary directories are required. No provider secrets in shell arguments, journal logs, image build arguments or user-data/cloud-init. A privileged host administrator remains inside the trust boundary.

## Authority, expiry and activation evidence

`enabled` requires a named approval reference and original absolute `approvedUntil`. There is no invented daily renewal or 25-hour hosted limit. This deadline is the actual operating authorization, not a renewal of the old local test window. The launcher stops services at that deadline and forwards termination to children, forcing child termination after 5 seconds. Configuration failures exit 78 and do not restart; operational failures have three restarts per 5 minutes. Normal shutdown/expiry does not restart. Linux systemd additionally kills the entire unit control group within 10 seconds (20 for the worker). The worker-only prestart/post-stop cleanup checks the recorded rootless daemon ID, exact `caselink-document-UUID` names and approved image digest before deleting any container. It runs even after operating approval expires or the worker group is killed, with each Docker command limited to 5 seconds. It never removes foreign names/images or uses another daemon; mismatch/failure blocks start and must alert. Keep the worker profile and rootless daemon available until cleanup is proved. The existing database processing controls, active accounts, consents, mandate limits, current facts, immutable packet bindings and transport permission checks still run at each side effect.

William Sanz confirmed individual operator and privacy/incident responsibility on November7 and expressly waived a separate privacy reviewer for the bounded Philadelphia SNAP pilot, conditional on engineering security readiness. Do not make a separate reviewer a prerequisite for this approved scope.

The separate web real-data gate, review collection flag and sender sending flag all remain false in the package. Setting JSON flags alone does not approve real-family processing or alter database/Auth gates. Before activation, finish the actual privacy/processor/notice review, incident and rights arrangements, approved cohort/operating window and engineering security assessment; verify exact program/transport authority and the complete release evidence. Medical-deduction and other health facts are in scope of that assessment. Sinch outbound document storage=false and retries=0 are necessary readbacks; they do not establish the provider's metadata/temporary-copy retention terms. Keep sender disabled until those terms and the selected destination route are resolved.

Retention uses a **different** approval reference/deadline, long enough to discharge the actual remaining deletion obligation after collection ends. Install/enable `caselink-parent-retention.timer` independently; it has no dependency on the worker/frontdoor/collection units. Its current bounded job deletes at most 1,000 eligible protected packets per run (ten batches of 100), with their linked keys, roughly once per minute after completion. The maximum protected PDF/key retention is 30 days from original consent; earlier withdrawal/account/grant/mandate limits win and viewing never refreshes it. Application/database guards make expired content unavailable at its deadline; physical deletion follows the maintenance run and is subject to host availability. Verify a successful post-expiry deletion on the actual release, alert on failed/missed cleanup or overdue rows, and retain the independent authority through outages. The protected timer does not replace ordinary record cleanup or establish processor/backup deletion.

The separate, disabled `ordinary-retention.example.json` and `caselink-parent-ordinary-retention.timer` prepare the existing ordinary cleanup path. Use its own `caselink-ordinary-retention` UID, private profile, dedicated NOINHERIT login granted only `parent_retention_worker`, and independently recorded maintenance authority extending through the actual obligation after processing closes. It uses S3 credentials instead of a project API/Auth key. [Supabase S3 access keys](https://supabase.com/docs/guides/storage/s3/authentication) bypass Storage RLS across all buckets: they are not provider-enforced bucket-scoped credentials. Keep this key in this service only; the code accepts only exact UUID paths in `parent-documents` and `parent-form-artifacts`, claimed by the existing restricted SQL cleanup functions. No broker HTTP deletion route, browser session or shared Auth deletion is added.

Ordinary runs have a one-minute execution bound and at most ten small claims (one document, artifact, account and request each per claim). Each S3 delete has a 15-second timeout and no automatic retry; shutdown/authority expiry cancels it. SQL acknowledges only confirmed Storage deletions; failures leave the lease for a safe retry. Existing database rules decide raw-file expiry, parent deletion and ordinary 90-day closed-request retention without extending any date. This mode does not purge protected PDFs/keys: keep their separate timer running. Both examples remain disabled and expired. No host schedule or physical deletion has been proved. Before activation, verify the actual project/region, separately provisioned credentials and role grants, authority deadlines, post-closure document/account deletion, preservation of shared Auth/school records, missed/failed-run alerts and recovery. Processor copies and backups require their own verified terms and deletion evidence.

After approvals, start one instance each of web/frontdoor/broker/review/worker, sender only when separately enabled, plus both independently authorized retention timers. Rehearse using synthetic fixtures before real intake: exact host and redirect origin; forwarded-header forgery; denial on public private ports; web process/env/file isolation; dedicated DB role refusal; parser isolation; stale/revoked mandate cancellation; sender unknown-delivery reconciliation; deadline shutdown; service restart; packet/key cleanup after collection shutdown; restore/recovery; browser mobile/accessibility and native PDF rendering. No provider send is implied by these commands. Record the release hash, parser digest, unit/config hashes, public build marker, installed systemd/Caddy/Node versions and test results without copying secrets.

## Stop and rollback

Stop `caselink-parent@frontdoor`, `@review`, `@worker` and `@sender` to close collection and future work; revoke the relevant current database/provider authority when required by the approved incident/withdrawal procedure. A process stop alone cannot retract a request already accepted by an external carrier. Preserve immutable receipts and reconcile unknown delivery before retry. Keep both independent retention timers and their separately approved maintenance configurations active until their respective cleanup obligations are proved. Roll back only to a schema-compatible reviewed source release and matching public build marker; never roll database migrations back blindly or restore stale authority. Remove host/DNS access and delete the billable VM only after the applicable retention/recovery obligations and secret revocation are completed. No purchase, DNS edit, database migration, provider action or service activation has been performed by preparing this package.
