## What is reused

The parent experience uses the existing Supabase project, Auth identities, email addresses and passwords. No credentials are transferred between providers, no identities are duplicated and no school data or existing roles are changed. The parent sign-in form defaults to the existing CaseLink email/password. Existing-account mode disables email-code entry unless explicitly configured after enrollment review. Existing school identities use their password or the existing password-reset flow.

The parent server keeps its `caselink-parent-auth` HttpOnly cookie. It authenticates against the same identity provider without overwriting the legacy browser client's cookies or silently treating a school-workspace cookie as permission to begin parent work. Normal parent sign-out revokes the current parent session, not every session for the identity. The school session remains subject to its existing password, live-session and active-account checks.

In shared-account mode, “Forgot your password?” reuses `/forgot-password`, the verified `/auth/callback` exchange and `/reset-password?mode=recovery`. The existing reset flow updates the password and signs out all sessions before returning to `/login`. That entry point sends the parent deployment back to `/sign-in` with only a fixed success or invalid-link notice. It keeps the school deployment's behavior unchanged. Resetting the password never reactivates a disabled legacy account or bypasses the requirement for a fresh password sign-in.

For a legacy `app_users` identity, the database additionally requires an enabled shared-account setting, an active legacy account and a password authentication method signed by Supabase Auth. An invitation, recovery or email-code-only session does not bypass the old password requirement. A deactivated legacy account cannot continue through the parent app. Current service mandates and queued notices also recheck this status, including the limited completion-notice exception for a recently closed request.

Authentication creates or reads only that identity's own empty parent-support household. It does not copy a school family into the household, make the user a parent of a school record, or give an administrator access to other parents. A support request still needs the separate informed mandate. Existing parent ownership, referral scope, processing approval, document consent, revocation and deletion checks remain in force.

Initial authorization and renewal quote their deadline from an authenticated database-issued window for up to 30 days. The web API also validates against that database clock; a family's device clock does not extend permission or cause a valid request to exceed the database ceiling. An interrupted initial start keeps its exact quoted packet and idempotency key. Explicit shorter expiries remain unchanged, and the database still validates the final operation.

### Separately approved background planning and assistant

`parent:connected:services` is the opt-in private-service launcher for the owner-approved extension. It is separate from the secret-free web server. It validates an owner-only configuration in the ignored runtime area, exact approved existing provider, existing-account mode, loopback site/broker origins, verified database TLS and a future recorded deadline. It launches the restricted planning/assistant worker, private Storage broker and periodic parent-retention process; the launcher stops its children at the configured deadline. Database processing approval, current membership/account, identity cutoff and request-specific authority remain independent checks. A running local process cannot extend database approval, widen enrollment or enable a partner route.

The broker and retention process still hold the existing project-wide service/secret key for Storage. Their restricted SQL logins do not narrow that key's separate [Storage RLS bypass](https://supabase.com/docs/guides/storage/security/access-control) or [Auth administration authority](https://supabase.com/docs/reference/javascript/auth-admin): they remain trusted administrative boundaries, and compromise could affect shared school data or Storage. The web server and planning/assistant worker never receive this key. This residual risk requires operational controls and release review; the localhost approval does not authorize a new credential or prove full isolation from a compromised administrative process.

Before starting, record the exact owner-approved 24-hour deadline, finite shared model-call cap, applicable per-account limits and private restricted service principals. Configure the database's budget start/call ceiling explicitly; an absent configured project ceiling is not an acceptable capped pilot. The separate 30-call synthetic evaluation authorization is not unlimited runtime capacity or permission to send actual household identifiers. Keep credentials/model keys in their required private process only and preserve payload-debug suppression; never copy them into Next's web environment, browser configuration, source control, verification artifacts or chat. Do not alter the shared project's global Auth hooks, enrollment, SMTP, redirect allowlist or existing passwords for this extension.

The worker records expiring health for planning and assistant availability. Request progress combines that health with saved jobs, personal steps and next-run information, and exposes queued, running, waiting, necessary-action, failed, paused/cancelled/closed or unconfirmed-service states. It does not simulate a progress percentage or equate a saved request with a sent application. Closing the page or normal sign-out preserves only work still allowed by its recorded mandate; pause, cancellation, expiry, offboarding and deletion stop the applicable future work.

Ask CaseLink uses the current owned request and a short, consented conversation to explain saved needs, recorded progress, necessary next steps, mandate limits and official program facts. GPT-6.1 Sol through Responses selects validated facts/actions; the server validates the selection and supplies attributed wording rather than accepting invented status or receipts. Detected identifiers/secrets are rejected before saving/model dispatch, context is minimized, Responses uses `store:false`, and per-request/account/project limits and cancellation apply. These safeguards do not establish zero retention by every processor or detection of every possible secret. Asking a question does not submit, change intake/permission, sign, restart cancelled work or grant access to another household; saved questions on an otherwise eligible inactive request remain explanatory.

## Auth enrollment and the global hook

Supabase's before-user-created hook is project-wide. **Do not replace an existing project's hook with `parent_before_user_created` or enable public signup globally just to activate this workflow.** The isolated parent local profile's hook and signup configuration are for that isolated environment.

Existing verified accounts do not require new Auth identities. Their password sign-in can be reused while preserving the existing enrollment policy. Before accepting new parents in the shared project, review the actual enrollment and invitation rules, existing hooks and approved parent-processing boundary together. Parent database RPCs and policies remain closed when processing is disabled; creating an Auth identity alone never grants a parent household or intake access. A family launch must verify both the intended Auth enrollment behavior and these database gates, not assume that a successful credential check proves readiness.

## Parent deletion preserves the shared identity

Parent-support deletion immediately stops future parent work and disables parent access. Cleanup erases the parent membership, requests, documents and eligible derived data under the documented retention policy. A purpose-scoped tombstone prevents automatic parent recreation during its retention period, including after restoration from an old backup.

The parent retention worker does **not** call Supabase Auth's `deleteUser`. The shared Auth identity, `app_users` record and school records are preserved. Deleting the Auth identity could cascade into unrelated school data or remove the person's existing login. Full identity or school-workspace offboarding belongs to its separate authorized process. Privacy notices must distinguish this retained identity from deletion of parent-support information; processor backups and recipient retention remain separate.
