# Existing CaseLink accounts and parent support

Updated October 26, 2026. This is an implementation and activation guide, not evidence that a hosted project has been changed or is ready for real-family processing.

## What is reused

The parent experience can use the existing Supabase project, Auth identities, email addresses and passwords. There is no password export, account duplication, school-data migration or change to school roles. The parent sign-in form defaults to the existing CaseLink email/password. An email code remains available for new or parent-only identities where the project's enrollment policy permits it. Existing school identities use their password or the existing password-reset flow.

The parent server keeps its `caselink-parent-auth` HttpOnly cookie. It authenticates against the same identity provider without overwriting the legacy browser client's cookies or silently treating a school-workspace cookie as permission to begin parent work. Normal parent sign-out revokes the current parent session, not every session for the identity. The school session remains subject to its existing password, live-session and active-account checks.

In shared-account mode, “Forgot your password?” reuses `/forgot-password`, the verified `/auth/callback` exchange and `/reset-password?mode=recovery`. The existing reset flow updates the password and signs out all sessions before returning to `/login`. That entry point sends the parent deployment back to `/sign-in` with only a fixed success or invalid-link notice. It keeps the school deployment's behavior unchanged. Resetting the password never reactivates a disabled legacy account or bypasses the requirement for a fresh password sign-in.

For a legacy `app_users` identity, the database additionally requires an enabled shared-account setting, an active legacy account and a password authentication method signed by Supabase Auth. An invitation, recovery or email-code-only session does not bypass the old password requirement. A deactivated legacy account cannot continue through the parent app. Current service mandates and queued notices also recheck this status, including the limited completion-notice exception for a recently closed request.

Authentication creates or reads only that identity's own empty parent-support household. It does not copy a school family into the household, make the user a parent of a school record, or give an administrator access to other parents. A support request still needs the separate informed mandate. Existing parent ownership, referral scope, processing approval, document consent, revocation and deletion checks remain in force.

Initial authorization and renewal quote their deadline from an authenticated database-issued window for up to 30 days. The web API also validates against that database clock; a family's device clock does not extend permission or cause a valid request to exceed the database ceiling. An interrupted initial start keeps its exact quoted packet and idempotency key. Explicit shorter expiries remain unchanged, and the database still validates the final operation.

## Explicit activation on an existing project

Do this first on a synthetic staging copy with no real family records. Live deployment, configuration and migration changes have not been performed by this implementation.

1. Preserve the existing project's backup, Auth enrollment policy, redirect allowlist and school regression evidence. Confirm the project is the intended existing CaseLink identity provider. Do not export or copy passwords or edit identities to manufacture matching accounts.
2. Review and apply the complete additive parent migration sequence, including `20261026033815_parent_existing_accounts.sql`, through the approved migration process. They introduce parent-owned tables and private worker functions; they do not reset school history. Review database advisors and effective grants/RLS on the actual Supabase version.
3. Select `CASELINK_PRODUCT=parent` and `CASELINK_PARENT_ACCOUNT_MODE=existing` in the parent web runtime. Set `NEXT_PUBLIC_SUPABASE_URL` and its public key to the intended existing project. Identify it in `CASELINK_SCHOOL_SUPABASE_URL`. Production must also match the approved `CASELINK_PARENT_PRODUCTION_SUPABASE_URL`, or the already-existing `CASELINK_PRODUCTION_SUPABASE_URL` if the parent-specific value is absent. HTTPS, exact site origin, HSTS and `CASELINK_PARENT_REAL_DATA_APPROVED=1` remain required for hosted processing. No admin, database, email or model secret belongs in the web runtime.
4. In a protected operator session, enable `parent_private.processing_controls.existing_accounts_enabled` only after the shared-account review. This flag defaults to `false`. The separate `enabled`, nonempty `approval_reference` and future `approved_until` processing controls must also be valid. Do not enable them merely to make a sign-in screen appear successful.
5. Give parent workers, storage broker and retention runtime the same account mode and approved project origins. Retain their separate restricted database principals, credentials, grants and approval settings. An existing project does not justify using the `postgres` or `service_role` database identity as the worker.
6. Rehearse the full Auth flow with synthetic accounts: existing password sign-in, failed password/rate limit, recovery/invitation restrictions, new permitted parent enrollment, revocation, inactive school account, cross-household denial, request creation, sign-out and purpose-scoped deletion. Test both reachable legacy routes and parent routes. Check the full service integrations separately.

Preview and test deployments still cannot point at the approved production database. Their own synthetic project may use the same shared-account structure. Local shared-project development supports the existing API/database ports `54321`/`54322` only with explicit existing-account mode; the default synthetic parent preview remains on `55321`/`55322`.

## Auth enrollment and the global hook

Supabase's before-user-created hook is project-wide. **Do not replace an existing project's hook with `parent_before_user_created` or enable public signup globally just to activate this workflow.** The isolated parent local profile's hook and signup configuration are for that isolated environment.

Existing verified accounts do not require new Auth identities. Their password sign-in can be reused while preserving the existing enrollment policy. Before accepting new parents in the shared project, review the actual enrollment and invitation rules, existing hooks and approved parent-processing boundary together. Parent database RPCs and policies remain closed when processing is disabled; creating an Auth identity alone never grants a parent household or intake access. A family launch must verify both the intended Auth enrollment behavior and these database gates, not assume that a successful credential check proves readiness.

## Parent deletion preserves the shared identity

Parent-support deletion immediately stops future parent work and disables parent access. Cleanup erases the parent membership, requests, documents and eligible derived data under the documented retention policy. A purpose-scoped tombstone prevents automatic parent recreation during its retention period, including after restoration from an old backup.

The parent retention worker does **not** call Supabase Auth's `deleteUser`. The shared Auth identity, `app_users` record and school records are preserved. Deleting the Auth identity could cascade into unrelated school data or remove the person's existing login. Full identity or school-workspace offboarding belongs to its separate authorized process. Privacy notices must distinguish this retained identity from deletion of parent-support information; processor backups and recipient retention remain separate.

## Verification and limits

Automated route and component tests cover password/code selection, bounded payloads, same-origin enforcement, generic credential errors, rate limits, local sign-out, database denial and safe redirects. Configuration tests cover explicit shared mode, approved origins, secret separation and synthetic preview/test boundaries.

The embedded PostgreSQL security fixture runs the actual parent migrations and the legacy password-session migration. It checks password versus OTP access for the existing identity, owner-only parent records, immediate offboarding effects on service grants and notices, and deletion preserving Auth/staff/school records while removing parent membership and requests and enforcing the tombstone. It does not substitute for Supabase Auth, Storage, simultaneous database connections, actual email delivery, hosted advisors or live partner tests. The default localhost preview uses a placeholder public key. The explicit actual-local-services mode connects only to the isolated synthetic services; neither mode connects to hosted school accounts.

Current provider references: [Supabase password sign-in](https://supabase.com/docs/reference/javascript/auth-signinwithpassword), [server-side Auth](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [before-user-created hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook), and [Auth user deletion](https://supabase.com/docs/guides/auth/managing-user-data#deleting-users). The current changelog was reviewed on October 25, 2026; no password API migration was required for the installed client.

Confirm both configured public key fields are public, email sending/rate limits work, confirmation/magic-link templates contain the expected code, and callback URLs use the intended site. |

The preserved school local profile has public signup disabled and does not configure the parent numeric-code confirmation/magic-link templates. Shared-account source compatibility does not activate new parent enrollment. Do not change that global policy silently to make a browser test pass. Agree and test the shared enrollment/template configuration before offering new parents a working signup promise.
