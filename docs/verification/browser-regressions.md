# Synthetic browser release checks

Run `npm run test:e2e` with CaseLink's isolated local Supabase stack running, Playwright Chromium installed (`npx playwright install chromium`), and Poppler available (`poppler-utils` on Ubuntu, `poppler` on Homebrew) for downloaded-PDF text checks. The runner builds the production application and uses port 3100, leaving other local applications alone. Its local-target assertions reject remote database, Auth, and mail addresses. CI runs this after the real database/Auth security checks.

The seven scenarios exercise invitation and password setup, invalid login and separate-browser password recovery; administrator MFA enrollment, bad codes, and returning verification; all twelve intake barriers; interruption and resumption of the same plan; recovery of an unsaved edit after refresh or session expiry; account-switch isolation; conflicting saves in two tabs; selective AI application; date confirmation and review; exact PDF download; stale-export denial; and the reachable case assistant. The web application receives no database-admin or service-role credential. AI HTTP responses are synthetic contracts; the real server actions, authorization, database writes, review checks, PDF renderer and browser download run unchanged.

Keyboard Tab/Enter activation and Axe WCAG 2 A/AA and 2.1 AA scans cover the account and casework screens and inline editors. Reflow checks use a 375-pixel viewport and CSS zoom at 200%, with screenshots for visual inspection. These do not substitute for school-device, screen-reader, browser-toolbar zoom, or school accessibility acceptance. Browser automation currently targets Chromium.

## October 14 result and corrected failures

All seven scenarios passed in 67 seconds. All 672 unit/component tests in 76 files, the full repository verification/build, and real local Auth security tests also passed. See `2026-10-14-browser-regressions.json` for the machine-readable browser record. The full workflow reports no uncaught page errors. A sanitized database denial appeared during the deliberately revoked-session scenario; no old-session data or another account's draft was exposed.

The run reproduced and repaired missing inline field names, lost focus after cancelling review, and a production-only PDF failure. The PDF layout engine requires WebAssembly; production now permits `wasm-unsafe-eval` while still forbidding JavaScript `unsafe-eval`. This distinction follows [the browser CSP documentation](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src#unsafe_webassembly_execution). Native dialogs stay mounted for focus restoration and use the browser's top layer, avoiding a portal-induced hydration mismatch. The assistant previously redirected to the plan without an entry point; the plan now opens the existing, authorized assistant, with unsaved edits protected and a return link.

The downloaded PDF's SHA-256 matches the actual blob assigned to the preview, and its pages and title are validated. Capturing the blob observes the real generated bytes; it does not mock rendering or weaken CSP to fetch a blob in the test. A separate isolated Chromium check displayed the actual two-page browser download under the unchanged `object-src 'none'` policy, and the rendered pages were visually inspected. The larger text/layout/monochrome corpus remains `npm run test:pdf`.

The first harness attempts also had incorrect selectors for the native alert dialog, Waiting explanation, and legacy assistant URL. Those assertions were corrected against the actual UI; failing scenarios remain enabled, with no retries masking failures. CI disallows focused tests. Exact hosted-candidate CI, real email delivery/scanning and school acceptance remain CL-16/CL-34/CL-41, not conclusions from this local run.
