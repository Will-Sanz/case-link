## Protected lifecycle and document boundary

Four PECO-purpose controls remain off by default. Start and the first private revision are atomic. Original dates survive reuse and reordering. Same-key exact retries reconcile without another revision; superseded retries cannot revive an old account or preparation. Corrections invalidate queued older work. Raw private values stay out of chat, ordinary facts, worker claims and routine packets. This is private database JSON with restricted access, not separately envelope-encrypted bytes; database/hosting administrators and backups remain part of the exposure.

An owner-only metadata flag keeps the saved-answer view reachable if collection closes or the request mandate later changes. It contains no raw answers and is not a worker/model field. Owner JSON export includes all immutable revisions and their consent/provenance; unrelated households and school roles cannot read them. Parent-purpose deletion cascades through these rows while preserving a shared Auth identity. Existing overall processing closure still blocks normal owner read/export; deployed rights handling, processor retention and scheduled erasure require their own operating evidence. Request retention does not become indefinite merely because answers are read or a new request starts.

The new document boundary is based on the existence of private PECO history, so later mandate changes or a closed purpose cannot reopen ordinary upload/processing. The API rejects before parsing; metadata registration/confirmation, Storage insertion and the document broker independently enforce it. Previously stored private bytes cannot be claimed for routine processing. Existing owner history/deletion and separately consented ordinary utility/SNAP document paths remain. Private income-proof intake is still unimplemented; ordinary upload is not a substitute.

The existing offline PECO draft/income renderer now rejects mismatched people/account/snapshot references and preserves the earliest source deadline. A real owned source resolver, private rendering/artifact-lifetime channel and validated income-evidence adapter remain unimplemented. Accepted personal certification, protected required fields, exact delivery and provider/account status remain distinct required work.
